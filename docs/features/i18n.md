# Internationalisation

Remoter ships in ten languages from v1.0. The rationale is in
[ADR-0008](../architecture/decisions/0008-internationalisation.md); this
document is the working detail.

## Supported locales

| Locale | Language | Direction | Plural forms |
|---|---|---|:---:|
| `en` | English | LTR | 2 |
| `zh-Hans` | 简体中文 | LTR | 1 |
| `es` | Español | LTR | 3 |
| `hi` | हिन्दी | LTR | 2 |
| `ar` | العربية | **RTL** | **6** |
| `pt-BR` | Português (Brasil) | LTR | 3 |
| `ru` | Русский | LTR | **4** |
| `fr` | Français | LTR | 3 |
| `de` | Deutsch | LTR | 2 |
| `tr` | Türkçe | LTR | 2 |

Arabic's six plural forms and Russian's four are why message formatting uses ICU
MessageFormat rather than an `if (n === 1)` check. There is no shortcut that
produces correct grammar in these languages.

## Stack

- **`i18next` + `react-i18next`** with **`i18next-icu`** over
  **`intl-messageformat`** for ICU MessageFormat. The two ICU packages are MIT
  and BSD-3-Clause respectively, and their transitive `@formatjs/*` and `tslib`
  dependencies are MIT and 0BSD — all GPL-3.0 compatible
- **`Intl`** for every date, time, number, currency and relative-time value.
  No hand-rolled formatting anywhere in the codebase; the implementations live
  in `apps/desktop/ui/src/i18n/format.ts` and every one of them takes the
  locale as an argument rather than reading a module-level "current" one
- **JSON catalogs** at `locales/<locale>/<namespace>.json`, namespaced by
  feature. One namespace per directory under `apps/desktop/ui/src/features/`,
  plus two that cut across all of them:

  | Namespace | Covers |
  |---|---|
  | `common` | Strings belonging to no single screen: actions, separators |
  | `shell` | Title bar, tab strip, status bar, footer, inspector, empty and locked states |
  | `settings` | The application settings screen and its six sections |
  | `connections` | Tree, editor, command palette |
  | `sessions` | Tabs, terminals, transfers, host-key prompts |
  | `vault` | Picker, unlock, creation, recovery key |
  | `vaultsettings` | Key slots, rotation, auto-lock, recording, backups |
  | `audit` | Audit viewer, filters, export |
  | `import` | The import wizard |
  | `errors` | IPC failures, keyed by `IpcError.code`. See below |

  The list of namespaces is declared once, in `src/i18n/locales.ts`. A screen
  names the one it needs — `useT("settings")` — and only that catalogue is
  fetched, so opening Settings does not also parse the import wizard's copy.

  `shell`, `audit`, `import` and `vaultsettings` were added to the original
  list of seven when the layer was built: the shell has copy of its own that
  belongs to no feature, two features that existed by then had none, and the
  vault's own settings screen turned out to be a screen rather than a corner of
  `vault`.

  Declaring a namespace in `locales.ts` does not create it. A namespace becomes
  askable from `useT()` when `locales/en/<namespace>.json` exists *and* has a
  line in `src/i18n/i18next.d.ts` — in that order, so a screen cannot be
  written against a catalogue nobody has filled in yet. Everything downstream
  is derived from what English actually ships (`SHIPPED_NAMESPACES`), including
  which languages are selectable, so adding a namespace to English makes every
  translation incomplete until that file is translated too. That is the
  intended behaviour and worth knowing before you add one.
- **Weblate** for the translation workflow, so translators never touch Git
- **Nothing on the Rust side.** This document used to say the core used
  `fluent`. It does not, and never did: `fluent` appears in no `Cargo.toml` in
  the workspace, and there is no message catalogue, no locale loader and no
  translated string in any crate. Every user-visible sentence in this
  application is produced by the frontend, from the JSON catalogues above.

  What crosses the IPC boundary instead is structured. An `IpcError`
  (`crates/remoter-ipc/src/error.rs`) carries a stable dotted `code` — ASCII,
  never displayed, never translated — plus an English `message`, an optional
  `detail` for the "copy details" affordance, and the actions the interface
  should offer. The interface branches on the `code` and renders the sentence
  for it from the `errors` catalogue. The locale itself is one string on the
  settings record (`AppSettings.locale`): the core validates that it is not
  empty, stores it and hands it back, and never reads any meaning into it.

  So the division is not "some strings here, some there". It is: **prose in the
  frontend, identifiers in the core.** The Rust `Display` implementations,
  `detail` strings and panic locations stay English on purpose — they are
  diagnostic text, read by whoever is debugging and by tooling, which is the
  same reason the exported audit log stays English

### The accessor

`useT(namespace)` from `@/i18n`, and nothing else. It is typed against the
English catalogues (`src/i18n/i18next.d.ts`), so a key that does not exist is a
compile error and a namespace with no catalogue cannot be asked for at all.

Interpolated values go in the options object. They are substituted as **data**:
`intl-messageformat` parses the *message* into an AST and inserts arguments
into the result, so a hostname, a MOTD line or a file name containing `{`, `#`
or `<script>` cannot become message syntax or markup. React escapes what
reaches the DOM, and `dangerouslySetInnerHTML` is an ESLint error with no
override. `src/i18n/interpolation.test.ts` pins each of those down.

### When a key is missing

In order: the chosen language, then English, then — only if English does not
have it either — the key's last segment, humanised, wrapped in `⟦ ⟧` in a
development build and plain in a release one. Never the raw key, never a throw,
and `console.error` in development naming the file to add it to. A message that
will not *parse* falls back to the English source of the same key rather than
putting ICU syntax on screen. `src/i18n/missing.ts`.

### Failures

The core's failures are the one surface where the text does not originate in
the catalogue, so they get their own rule. `IpcError` carries a stable dotted
`code`, an English `message`, an optional `detail` and an ordered list of
actions; `locales/<locale>/errors.json` is keyed by that code and holds the
sentence and the action labels. `useFailureText` (`src/i18n/failures.ts`) joins
them, and `FailureNotice` (`src/components/FailureNotice.tsx`) is the component
that renders the result — the callout with the sentence, the diagnostic and the
suggested actions as a list.

**A screen renders a failure through that lookup and never renders
`IpcFailure.message` itself.** Usually that means `FailureNotice`. Two places
in the interface have no room for a callout — the status bar's one line, and a
refused rebind inside a row of the shortcut table — and they call
`useFailureText` directly and lay the sentence out themselves. That is the
whole permitted set: same text, same catalogue, different frame. This paragraph
used to say "`FailureNotice` is what every screen renders", which was not true
of any of them: the connection tree rendered the core's English for a failed
load, a failed move (message, diagnostic, *and* the action list flattened into
prose with a separator of its own) and a failed delete, and so did the status
bar and the shortcut table. Every one of those codes had a complete translated
entry sitting unused.

`src/i18n/failures.rendering.test.ts` now reads the components and fails on a
`.tsx` that touches `message`, `detail` or `actions` on anything named like a
failure or declared `IpcFailure`. The catalogue guard proves the sentences
exist; this one proves somebody renders them. Neither is worth much alone.

The rules the lookup applies:

- **A code the catalogue knows** renders the catalogue's sentence and labels.
- **A code it does not** renders exactly what the core sent. A failure added in
  Rust therefore appears in English until someone translates it, rather than as
  a blank callout or a raw `vault.kdf-params-refused`.
- **`detail` passes through.** It is a machine diagnostic — an OS error string,
  a node id, a Rust `Display` — and it is what a reader copies into a bug
  report. A translated one is useless to whoever reads that report.
- **Actions are positional**, matching the order the core offered. An entry
  short of a label leaves that one action as sent.
- **English is served from the core, not the catalogue.** The core's sentence
  is the catalogue entry with its specifics substituted in — "after 15
  minutes", the actual path, the byte offset — and those cannot be recovered
  from the finished string, so the catalogue entry is necessarily the same
  sentence generalised. An English reader loses nothing by keeping the core's.
- **The core's text never goes through `t()`.** It contains values a user or a
  remote host chose, and one `{` in a file name would be ICU syntax.

`src/i18n/failures.catalogue.test.ts` parses `crates/remoter-ipc/src/error.rs`
and fails if any code it can emit has no entry, in any shipped language, or if
an entry labels a different number of actions than the core offers. Adding a
code in Rust and forgetting the catalogue is a red build, not a sentence that
turns up in English in a screenshot six months later.

### Sentences the core used to write

The failure path is the *pattern*, not the only place it applies. Anywhere the
core composes a sentence and the interface prints it verbatim, the catalogue
can never reach it — and because the sentence looks finished on an English
machine, nothing says so. Three of them were doing exactly that, two on the
first screen of the application:

| Field | Now also carries | Composed from |
|---|---|---|
| `RecentVault.unreachableReason` | `unreachableKind` (`missing`, `unreadable`, `not-a-file`), `unreachableDetail`, `unreachableCode` | `vault:picker.unreachable.*` |
| `RecentVault.syncWarning`, `VaultProbe.syncWarning` | `syncProvider` — a brand name, never translated | `vault:detail.syncWarning` |
| `SearchHit.subtitle` | `subtitleKind` (`items`, `members`), `subtitleCount` | `connections:palette.subtitle.*`, as an ICU plural |

The rules are the failure path's, unchanged. The kind is stable lower-case
ASCII and is never displayed. The English stays on the DTO as the fallback for
a kind the interface does not know, and is documented in `lib/ipc.ts` as
not-for-rendering, the way the `PasswordStrength` fields below are. The
diagnostic — an operating-system error string — passes through in English,
because it is what a reader copies into a bug report.

One case is expressed as a failure rather than a kind: a remembered vault whose
file is there but does not read as a vault arrives with `unreachableCode` set
to the probe's `IpcError.code`, because `errors.json` already holds a
translated sentence for every code the core can raise. That is a better
sentence than any generalisation the picker could write, and it costs no new
catalogue entry.

`src/i18n/composed.catalogue.test.ts` is the drift guard, and it is the same
guard `failures.catalogue.test.ts` is: it reads the `as_str` literals out of
`UnreachableKind` (`recents.rs`) and `SubtitleKind` (`commands.rs`) and fails
if a kind has no entry in any shipped language, if an entry has stopped naming
the value it is composed around, or if the English catalogue still labels a
kind the core no longer sends. The Rust side pins the identifiers in a unit
test of its own, so a rename is caught from both ends.

Two English fields on `PasswordStrength` are treated the same way and for the
same reason: `label` ("Fair") and `explanation` ("Centuries of guessing at a
billion attempts a second."). Neither is rendered. `useStrengthText`
(`src/i18n/strength.ts`) derives both from the entropy estimate the core also
sends, through `common.strength.*`, which additionally makes the count an ICU
plural — so it inflects, and its digits follow the locale's numbering system.
The thresholds mirror `score_for` and `consequence` in
`crates/remoter-ipc/src/commands.rs`.

### The guard

`remoter-i18n/no-literal-jsx-text` and `remoter-i18n/no-text-constant`
(`apps/desktop/ui/eslint-rules/`) fail the build on a user-visible string
written into JSX, and on the per-file `const TEXT = { … }` object that was this
codebase's habit before extraction. Both are errors everywhere except the
directories listed in `eslint-rules/i18n-baseline.js`, where they are warnings
until that feature is extracted — **delete your feature's line when you extract
it**. That list is now empty: every feature directory is extracted, and a new
entry in it should be read the way a new `@ts-expect-error` is. Things that are
genuinely never translated (see below) take an ordinary `eslint-disable`
comment with a reason.

`no-literal-jsx-text` covers JSX text, the DOM's visible attributes (`alt`,
`title`, `placeholder`, the `aria-*` strings) **and component props that carry
copy**. The last of those cannot be a fixed list: a component invents a prop
name for a piece of copy, and a list only learns it after English has been
written into it — which is a guard that arrives after the string it was meant
to stop. So the rule matches a suffix family as well as a set of single words:
anything ending in `Label`, `Text`, `Title`, `Note`, `Message`, `Description`,
`Reason`, `Heading`, `Warning`, `Error`, `Hint`, `Lead`, `Legend`, `Prompt`,
`Caption`, `Summary`, `Subtitle`, `Tooltip`, `Placeholder`, `Help` or `Alt` is
user-visible, as are `body`, `note`, `lead`, `reason`, `refusal`, `warning`,
`where` and their like. **Name a copy prop compositionally and the guard covers
it for free.** Only *literals* are ever reported, so a prop holding a value —
`label={t("…")}`, `warning={warning}` — is untouched whatever it is called.

## Message format

```json
{
  "session": {
    "active_count": "{count, plural, =0 {No active sessions} one {# active session} other {# active sessions}}",
    "connected_to": "Connected to {host} as {user}",
    "duration": "Connected for {duration}"
  },
  "vault": {
    "_comment_recovery_warning": "SECURITY-CRITICAL. Must not be softened. See docs/security/key-management.md.",
    "recovery_warning": "This is your only way back in. If you lose your master password and this recovery key, your vault cannot be opened — not by you, not by us, not by anyone."
  }
}
```

Rules:

- **No string concatenation.** `"Connected to " + host` breaks in every language
  with a different word order. Interpolate through the message
- **Keys are semantic**, not English text. `vault.recovery_warning`, never
  `"This is your only way back in"`
- **Every non-obvious key gets a translator comment** as a sibling
  `_comment_<key>` entry. Translators cannot see the UI
- **A security-critical string is marked where it lives**, with a `_comment_`
  that says SECURITY-CRITICAL and what must not be softened — as above. There
  was going to be a `security` namespace for these, and the registry listed one
  for a milestone without a file behind it; the namespace was dropped in the
  localisation milestone. Collecting them in one file would have split each
  screen's copy across two catalogues while doing nothing the comment does not,
  and the comment has the advantage of being shown to the translator at the
  moment of translating and of being unable to drift away from the string it
  guards. A translation that softens one of these is rejected in review
- **Only `locales/en/` is edited by contributors.** Other locales come from
  translators through Weblate

## Right-to-left

Arabic is RTL, and supporting it properly means committing to logical CSS
throughout rather than bolting on a mirrored stylesheet.

- `dir="rtl"` on the document root; everything else follows from that.
  `applyDocumentLanguage()` writes it, along with `lang`, and nothing lower in
  the tree sets either
- **CSS logical properties everywhere**: `margin-inline-start` not
  `margin-left`, `padding-inline-end` not `padding-right`, `inset-inline-start`
  not `left`. As of the localisation milestone the frontend contains **no**
  physical directional property — the audit is a `grep` and it returns nothing
- Anything a logical property cannot express goes through a token.
  `--dir-flip` is the horizontal sign (`1` / `-1`) for a transform, so a panel
  that slides in from the inline start uses
  `translateX(calc(var(--dir-flip) * 8px))` rather than its own `[dir="rtl"]`
  rule; `--dir-arrow` is the chain glyph for CSS content. Both are in
  `styles/tokens.css`, and the interface-copy equivalent of the second is
  `common.punctuation.chainSeparator` in the catalogue
- Icons that indicate direction (back, forward, expand, collapse) mirror; icons
  that represent objects (a server, a key, a folder) do not. The set is
  declared once, in `components/Icon.tsx`, and the mirroring is one rule in
  `styles/base.css` driven by `--dir-flip`
- Terminal and framebuffer content is **never** mirrored — it comes from the
  remote host, which has its own directionality
- Numbers, hostnames, IP addresses, paths and code stay LTR inside RTL text,
  using Unicode bidi isolation rather than hoping the browser guesses
  correctly. `isolate()`, `isolateLtr()` and `isolateChain()` in
  `src/i18n/bidi.ts` are the only places those code points appear, and they are
  written as escapes. Apply them at the call site, to values that came from the
  vault or from a remote host — never to interface copy, which is already in
  the document's direction
- A test asserting on a sentence with an isolated value in it needs
  `withoutBidi` from `src/test/bidi.ts` as its query normaliser, or it will
  fail to match for a reason nobody can see

RTL is checked in CI with a visual regression run over the main screens.

## Locale-specific hazards

**Turkish dotted and dotless I.** Turkish writes four letters where English
writes two: `I`/`ı` and `İ`/`i`, and the shift key maps them crosswise.
JavaScript's `toLowerCase()` is not locale-sensitive — it applies *English*
rules to every language — so `"ANLIYORUM".toLowerCase()` is `"anliyorum"`,
which is not the word `"anlıyorum"` the reader typed, and
`"İ".toLowerCase()` is an `i` with a separate combining dot that nobody typed
and nobody can see.

The fix is in one place, `src/i18n/fold.ts`, exported from `@/i18n`. **Every
case-insensitive comparison of text a person reads goes through it**, and
nothing else in the interface rolls its own:

```ts
// Wrong — English rules, whatever the interface says
if (a.toLowerCase() === b.toLowerCase()) { … }
if (haystack.toLowerCase().includes(needle.toLowerCase())) { … }

// Right — whole-string comparison, case forgiven in this language
if (equalsIgnoringCase(a, b, locale)) { … }

// Right — substring matching, folded the same way on both sides
if (foldForSearch(haystack, locale).includes(foldForSearch(needle, locale))) { … }

// Right — an ASCII identifier: a key cap, a query prefix, a tag used as a flag
if (foldInvariant(tag) === "favourite") { … }
```

The last of those is not a detail. A tag this application reads as a flag, a
`tag:` prefix and the `Ctrl` on a key cap are not words in anyone's language,
and folding them in the reader's turns `FAVOURITE` into `favourıte` and a
key cap's `I` into a letter no keyboard has. The shortcut table folds each row
twice for exactly this reason: its prose in the reader's language, its key caps
invariantly.

`foldForSearch` also folds `ß` to `ss` (so `strasse` finds `Straße`),
folds Greek's two sigmas together, and strips combining marks — which is what
makes search diacritic-insensitive, and is applied to needle and haystack alike
so it can never make a search find less.

What stays outside all three is text that is not language: a file path
normalised before two of them are compared, a recovery key reduced to
`[0-9A-Z]`, a protocol name shown in capitals. Those are ASCII by construction
and `toLowerCase`/`toUpperCase` is the right tool for them — but the moment
either side of a comparison could contain a letter a translator or a user
wrote, it is the wrong one.

**Both were shipped wrong.** The typed confirmation that gates removal of the
recovery key slot folded with `toLowerCase()`, so the Turkish sentence typed in
Turkish capitals was *refused* while the English one was accepted — on the one
deletion with no way back, against a hint that promises capitals do not matter.
The connection tree, the command palette, the import preview and the shortcut
table all folded search the same way. `src/i18n/fold.test.ts` holds the cases,
in Turkish, German, Greek and Arabic.

In Rust, `str::to_lowercase` is locale-independent and therefore safe for
comparison, but must not be used to *display* lowercase text to a Turkish user.

**German compound nouns** run roughly 35 % longer than English. Layouts must
flex; fixed-width buttons will break. Pseudo-localisation in CI expands strings
by 40 % and wraps them in markers, which catches truncation before a translator
ever sees it.

**CJK line breaking** differs from Latin. `word-break` and `line-break` are set
per script rather than globally.

**Arabic and Devanagari** need more line height than Latin. The type scale
defines per-script line-height overrides rather than one global value.

## What is never translated

- Protocol names: SSH, RDP, VNC, SFTP
- Key names: Ctrl, Alt, Shift, Esc, F4, Page Up. A key cap names the physical
  key the user is being asked to press, and the words are the ones printed on
  the keyboard in front of them — translating "Esc" would name a key that does
  not exist. `KEY_LABELS` and `MODIFIER_LABELS` in
  `apps/desktop/ui/src/hooks/keyboard/accelerator.ts` are the whole set
- Hostnames, IP addresses, ports, file paths
- Terminal output and framebuffer content — it belongs to the remote host
- Log entries in exported audit files, which stay English for tooling
- **Error codes** — `vault.locked`, `import.parse.failed`. They are stable
  identifiers the interface branches on, they are never displayed, and nothing
  about them is language. The *sentence* shown for one is translated: it comes
  from the `errors` catalogue, keyed by the code. The English `message` the
  core attached travels alongside and is what the interface falls back to when
  the catalogue has no entry for that code — the same fallback a missing key
  gets, for the same reason
- The `detail` on a failure, which is the underlying diagnostic verbatim
- Personal names and licence abbreviations inside a credit. The terminal
  palettes are somebody's published work, and "Ethan Schoonover, MIT" reads the
  same in every language. The credits themselves *are* catalogue strings
  (`settings:terminal.palettes.*`), because most of them are sentences with a
  name inside rather than a bare attribution; the translator note on that block
  says which words to leave alone

## Adding a language

The barrier is a committed translator, not a technical change:

1. Add the locale to `SUPPORTED_LOCALES` in
   `apps/desktop/ui/src/i18n/locales.ts` — code, endonym and direction
2. Create `locales/<locale>/` from the English catalogs
3. Add the locale to the Weblate project
4. Verify plural rules and direction
5. Run the pseudo-localisation and RTL checks

There is no sixth step to make it selectable. **Availability is measured, not
declared**: a language is offered the moment `locales/<locale>/` holds every
namespace English ships (`isLocaleAvailable`, in `src/i18n/catalogues.ts`), and
the Language screen counts the available ones for the sentence it shows. The
screen previously carried a hardcoded `available: false` on nine languages,
which meant the first thing to happen after a translation shipped would have
been the interface continuing to call it unavailable.

All ten are complete as of the localisation milestone, so every row on that
screen is selectable today. Nothing in the code says so, and nothing should.

**The same trap catches copy and tests, and it caught both.**
`settings:language.progress` used to end "The rest are listed because
translation is under way… until then choosing it would change nothing" — true
when it was written, translated faithfully into nine languages, and false in
all ten by the time anyone read it. It is now written as a conditional ("any
language still being translated…") that holds whether nine languages are
outstanding or none. And `catalogues.test.ts` asserted that every locale but
English was unavailable, which turned the arrival of the translations into a
failing test on correct code; `language.test.tsx` named Hindi as its example of
a language with no catalogue. Both now assert the *rule* — an available
language is selectable, an unavailable one is refused, whichever those are
today — and neither names a language. A test that has to be edited every time a
catalogue lands is a test that gets deleted by whoever is in a hurry.

The floor that check enforces is presence, not completeness: a namespace file
that exists but is half translated passes it, and its missing keys then fall
back to English one by one rather than leaving blanks. Judging *completeness*
is Weblate's job, and the rule that partial translations mixed with English are
worse than English alone still applies to the decision to publish a catalogue
at all.

Security-critical strings are flagged in the catalogs and reviewed separately.
A warning about permanent data loss that a translator has softened into
something gentler is a real, and entirely foreseeable, source of harm.
